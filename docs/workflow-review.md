# 실제 업무 흐름·화면 이해도 점검

2026-09-13. 이번 점검은 개별 버튼의 동작 여부보다 **찾기 → 확인 → 등록·수정 → 저장 → 원래 화면에서 재확인**이 자연스럽게 이어지는지에 초점을 맞췄습니다. 운영 고객·매물·업무 자료를 쓰기 검사의 대상으로 삼지 않았습니다.

이전 [검색 정확성 점검](search-review.md)과 [가독성 점검](readability-review.md)에 이어 수행한 기록입니다. 자동 검사 수와 최종 실행 상태는 [README](../README.md#숫자로-보는-현재-구현)와 GitHub Actions에서 확인합니다. 검사 수만으로 모든 실사용 오류가 없다고 판단하지 않습니다.

## 어떤 문제가 있었고 어떻게 바꿨나

### 추가 점검: 엑셀 달력·매물 수정 이력·읽기 우선

같은 날 이어진 요청으로 두 원본 XLSB의 달력 VBA를 읽기 전용으로 대조했습니다. 매물 관련 5종은 주소, 계약·금전 5종은 주소와 물건지·업소, 나머지는 고객을 먼저 보여 주는 규칙과 부동산 고객 예외를 반영했습니다. 상세 기준은 [엑셀 분석](excel-analysis.md#달력의-업무종별-표시-기준)에 기록했습니다.

- 업무를 선택하면 입력란 없는 읽기 화면을 먼저 엽니다. 수정은 명시적인 **업무 수정** 버튼으로 시작하며 취소·저장 뒤에는 읽기 화면으로 돌아갑니다.
- 업무일지·달력·통합검색·고객 이력·홈·업무현황에서 묶음의 모든 주소를 표시합니다. 검색 일치 표시는 해당 물건에만 붙이고, 각 물건 이력은 그 주소의 식별키로 연결합니다.
- 읽기 화면은 최대 10개 물건의 주소·가격·물건지·업소를 기본 펼침으로 보여 줍니다. 선택한 보조 이력 위치로 초점을 이동하고, 닫으면 누른 버튼으로 돌아갑니다.
- 매물 관리의 **매물 수정 이력 추가**는 기존 업무를 덮지 않는 새 기록입니다. 현재값은 가장 최근 업무일의 이력으로 계산하며 과거 정정과 새 변경 이력을 구별합니다.
- 실제 SQLite 재현에서 매물 갱신 오류 뒤 업무·이력만 남는 부분 저장을 확인했습니다. 업무·물건·이력·현재 매물 갱신을 같은 D1 batch로 묶어 전부 성공 또는 전부 취소하도록 수정했습니다. 현재 매물·이력 및 업무·세부 물건 조회도 각각 같은 batch에서 읽습니다.

추가 후 자동 검사 **277개 통과**. 강제 저장 오류의 전체 롤백, 같은 날 정정 순서, 과거 수정, 삭제 복원, 주소 변경, 묶음 중 한 물건 제거, 읽기 요청 경합, 뒤로가기, 10개 물건 전체 표시를 포함합니다.

합성 SQLite에 연결한 브라우저에서 두 물건 읽기 → 각 매물 이력 → 수정 취소·저장 → 읽기 복귀와 검색 조건 보존을 확인했습니다. 매물 수정 이력을 새로 저장한 뒤 현재 가격은 새 값으로 바뀌고 이전 두 이력은 보존되어 총 세 이력으로 표시되는 것도 확인했습니다. 달력의 단독·업소·부동산 고객 ID 표시와 열 물건 읽기 화면도 확인했으며 390px 모바일에서 페이지·대화창·본문 모두 가로 넘침이 없었습니다. 운영 자료에는 이 쓰기 검사를 하지 않았습니다.

### 앞선 전체 흐름 점검

| 실제 사용 흐름 | 발견한 원인·불편 | 수정·개선 |
| --- | --- | --- |
| 검색·필터를 바꾸고 결과 선택 | 새 조건을 입력한 뒤에도 이전 목록과 건수가 남거나, 조회 실패가 빈 목록처럼 보임 | 매물·고객·달력·할 일도 조회 조건과 결과 상태를 함께 관리. 새 조건의 대기·실패에는 이전 결과 숨김, 정상 0건과 오류 구분, 같은 조건으로 재시도. 갱신 중임을 별도로 알리고 CSV 잠금 |
| 화면 갱신이 겹치는 동안 업무 열기 | 다른 요청이 읽기를 취소하면 창이 열리지 않거나 계속 불러오는 상태로 남을 수 있음 | 새 업무·수정 창을 여는 데 필요한 참조 자료를 확인하고, 최신 열기 요청만 반영. 내부 조회 중단도 무한 로딩 대신 재시도 가능한 상태로 처리 |
| 업무 등록 중 새 고객 추가 | 고객 저장은 성공했어도 뒤이은 명부 조회가 실패하면 방금 만든 고객을 선택하지 못함 | 저장 응답의 고객을 명부에 즉시 반영하고 작성 중인 업무의 고객 선택만 변경. 고객 저장 성공과 보조 화면 갱신 실패를 구분 |
| 많은 고객 중 기존 고객 선택 | 관리 목록의 첫 1,000명만 사용하거나, 최근순 페이지 사이에서 순서가 바뀌어 고객 누락 | 선택 명부는 변경되지 않는 고객 ID 커서로 전량 수집. 수집 후 최근 업무·등록순으로 추천하고, 이름·ID 동률 기준은 기존 정렬과 일치 |
| 매물 관련 업무 저장 | 필요한 물건 정보를 다 입력하지 않아도 저장 직전까지 무엇이 빠졌는지 알기 어려움 | 화면과 서버가 같은 매물 관련 업무구분 목록을 사용. 일자 → 고객 → 업무구분 → 해당 물건의 필수항목 순서로 안내하고 누락한 입력란에 초점 이동. 일반 상담에 물건을 강제로 요구하지 않음 |
| 기존 매물로 새 업무 기록 | 이력에서 매물을 확인하고도 새 등록 창에 다시 입력해야 함 | 매물 이력에서 바로 업무 등록. 기존 매물 불러오기도 유지. 주소·가격 등 물건 정보만 옮기고 고객·상담 내용·매물 원문 메모는 자동 복사하지 않음 |
| 여러 물건을 작성하다가 한 행 삭제 | 입력한 행을 잘못 지우면 작성 내용이 바로 없어짐 | 내용이 있는 물건은 삭제 전 확인. 취소하면 해당 행과 다른 작성 내용 유지. 완전히 빈 추가 행은 바로 정리 |
| 업무·고객·할 일을 저장하며 이동 | 저장 중 화면이나 브라우저 뒤로가기를 눌러 처리 상태를 놓칠 수 있음 | 저장 중 이동·닫기 제한과 완료 안내 강화. 저장 실패에는 입력 내용을 남기고 다시 시도할 수 있게 함 |
| 검색한 업무를 수정하고 돌아오기 | 저장 후 조회 범위·검색 조건이 바뀌거나 날짜 이력의 업무구분 조건이 빠질 수 있음 | 현재 검색·기간·업무구분과 읽던 업무 범위를 유지해 갱신. 달력의 날짜 전체보기도 선택한 업무구분을 유지 |
| 홈의 숫자에서 실제 목록으로 이동 | 이전에 남긴 ‘종료 매물’ 필터 등이 적용되어 홈의 ‘진행 중’ 숫자와 다른 목록 표시 | 홈의 의미가 있는 바로가기는 해당 화면 조건을 맞춰 초기화. 일반 메뉴 이동은 기존 검색·필터 유지 |
| 가까운 일정을 모두 확인 | 홈·현황의 미리보기만 보이거나 월 경계에서 다음 달 일정 확인이 어려움 | 앞으로 7일·30일의 전체 예약·예정 업무를 가까운 날짜순으로 열기. 미리보기 수와 전체 수를 구분하고 월 경계를 넘어 조회 |
| 연락할 일을 수정하며 고객·매물 확인 | 연결 대상이 ‘선택한 고객/매물’로만 보이고, 목록 갱신 시 수정 행이 사라질 수 있음 | 연결 이름·주소와 이력 버튼 표시. 수정 양식을 목록 밖에 유지해 갱신·실패에도 초안 보존. 이력을 닫으면 작성 내용으로 복귀 |
| 할 일 완료·재개·예정일 변경 | 처리 안내에 대상이 없거나, 필터 숫자와 검색 결과 건수가 혼동됨 | 대상명을 포함한 안내, 완료 목록에서 다시 여는 위치 표시, 오늘·내일·날짜 미정 빠른 선택. 전체 필터 숫자와 현재 검색 결과 건수 구분 |
| 다른 할 일을 이어서 작성 | 같은 초안 교체를 부모·자식 화면이 두 번 확인 | 한 번 승인한 교체에는 재확인하지 않음. 승인 없는 교체와 저장 중 교체 보호는 유지 |
| 분류 추가·백업 생성 뒤 목록 확인 | 저장 성공 뒤 목록 조회만 실패해도 전체 작업이 실패한 것처럼 보여 중복 실행 위험 | 생성·저장 결과와 보조 조회 결과를 분리. 성공을 유지하면서 목록만 다시 불러올 수 있도록 안내. 재시도는 생성 요청을 반복하지 않음 |

## 한눈에 읽히도록 정리한 부분

- 화면 제목 아래에 역할을 설명하고, 현재 적용한 검색·상태·건수와 다음에 할 수 있는 동작을 구분했습니다.
- 업무 작성창 위에는 선택한 고객·업무구분·물건 수를 요약하고, 아래에는 저장·취소 버튼을 고정했습니다. 긴 양식을 끝까지 내려야 저장 버튼을 찾는 불편을 줄였습니다.
- 초록색 주요 동작과 기존 의미형 아이콘을 유지했습니다. 중요한 구분은 색만 바꾸지 않고 ‘조회 중’, ‘완료’, ‘기한 지남’ 등의 문구로 함께 표시합니다.
- 긴 주소·고객명·연결 정보는 줄바꿈해 표시하고, 이력의 긴 내용과 실행 버튼이 같은 가로 폭을 나눠 쓰지 않도록 유지했습니다.
- 할 일 수정은 목록과 별도 영역에서 이어갑니다. 조회가 실패해도 작성 중인 제목·메모·연결 대상은 남습니다.
- 고객·매물 관리의 표시 한도와 CSV 범위를 화면에 명시했습니다. 고객을 선택하는 전체 명부와 관리 화면의 최대 표시 수는 서로 다릅니다.

## 어떻게 검증했나

### 자동 회귀 검사

최종 타입 검사·배포용 빌드·자동 테스트 204개와 전체 코드 규칙 검사를 통과했습니다.

실제 API 처리기·바인딩 SQL을 메모리 SQLite에 연결하고, 실제 화면 코드의 렌더링·이벤트 처리기를 제어된 요청과 함께 검사합니다. 고정된 화면 문구의 존재 여부만 확인하는 방식은 아닙니다.

- 여러 물건의 주소 검색, 결과와 이력 대상 일치, 목록 조건·건수·페이지 유지
- 새 조건 대기·같은 조건 갱신·조회 실패·내부 취소·재시도·정상 0건 구분
- 새 고객 저장 응답의 즉시 반영, 업무 필수항목 안내, 물건 삭제 승인·취소, 초안 보호
- 1,001명 이상 명부 수집과 특수문자 ID 커서 처리, 2,000명 수집 중 업무 등록·이름 변경·앞쪽 삽입·삭제
- 과거 최근순 OFFSET 방식의 고객 누락을 부정 대조군으로 재현하고, ID 커서 방식에서 기존 고객을 유지하는지 비교
- 명부를 수집한 뒤의 추천 순서가 기존 SQL 최근 업무·등록순과 같은지 확인. 미래 예약이 추천 순서를 앞당기지 않는지도 포함
- 월 경계의 7일·30일 일정, 홈의 목적별 필터 초기화와 일반 탐색의 조건 유지
- 할 일 저장 실패·완료·재개·초안 교체, 분류 저장과 후속 조회 실패 구분, 백업 생성과 목록 조회 실패 구분

### 브라우저에서 이어서 확인한 흐름

실제 API와 합성 SQLite를 연결한 로컬 환경에서 업무·고객·할 일의 등록·수정 요청을 실행했습니다. 오류·지연은 테스트 환경에서 의도적으로 발생시켰습니다. 백업 생성·목록·다운로드 UI는 별도의 모의 응답을 사용했으며, 실제 운영 백업 생성·복원 검사가 아닙니다.

| 순회한 흐름 | 확인한 결과 |
| --- | --- |
| 새 고객 등록 성공 → 명부 조회 503 → 업무 작성 계속 | 새 고객 선택과 기존 업무 초안 유지 |
| 필수 매물 항목 누락 → 기존 매물 불러오기 → 작성한 물건 행 삭제 | 누락 항목 초점, 물건 정보 반영, 삭제 취소·승인 결과 일치 |
| 업무 등록·수정 → 저장 완료 → 업무일지로 복귀 | 합성 업무의 실제 저장 요청과 갱신, 검색 조건 유지, 저장 중 브라우저 뒤로가기 차단 |
| 달력 날짜의 9건 전체 이력 → 개별 업무 수정 → 이력 복귀 | 같은 날짜의 9건 목록을 유지하면서 저장한 내용 갱신 |
| 종료 매물 검색 → 홈 → 진행 중 매물 카드 | 이전 종료 상태·검색어를 초기화한 진행 중 목록 |
| 목록 요청 지연 → 503 실패 → 재시도 | 대기·오류·정상 결과 구분과 CSV 잠금 |
| 매물 이력 → 해당 매물로 업무 등록 → 작성 취소 | 매물 정보 반영, 고객·상담 내용 임의 복사 없음, 원래 이력으로 복귀 |
| 할 일 작성 → 연결 이력 → 복귀 → 등록·완료·재개 | 초안 유지와 각 처리 대상·상태 일치 |
| 홈 7일 전체 / 현황 30일 전체 일정 | 합성 8건 / 14건 전체 확인, 다음 달 일정 포함 |
| 설정 분류 추가 성공 → 분류 목록 조회 503 → 목록만 재조회 | 저장 성공 유지, 생성 요청을 반복하지 않고 정확히 1개 추가된 분류 확인 |
| 모의 백업 생성 성공 → 목록 조회 실패 → 재시도·다운로드 | 생성 성공과 조회 실패를 분리해 표시하고 생성 요청 중복 없이 후속 동작 |

390px 너비의 큰 글씨 모드로 홈·할 일·업무 현황·업무일지·매물·고객·달력·설정의 8개 화면을 확인했습니다. 점검한 화면은 페이지 전체 너비가 390px를 넘지 않았습니다. 긴 주소·긴 고객명이 있는 작성 화면과 이력은 캡처를 직접 확인했습니다. 모든 휴대폰·운영체제·브라우저 조합을 검증했다는 뜻은 아닙니다.

## 실제 자료 보호와 남는 한계

- 운영 업무 자료에 테스트용 등록·수정·삭제를 하지 않았습니다. 공개 코드·검사·문서에는 합성 자료만 사용하며 실제 고객명·연락처·비밀번호·운영 키·백업 파일을 넣지 않습니다.
- 운영 백업의 복원·재해 복구 훈련은 이번 범위에서 실행하지 않았습니다. 자동 검사와 백업 UI 검증만으로 실제 복구 성공을 보장하지 않습니다.
- 고객·매물 관리 목록은 여러 페이지를 읽고 CSV에도 읽은 목록을 저장합니다. 여러 페이지 조회 도중 다른 기기에서 자료가 바뀌면 동일 시점 스냅샷은 보장되지 않습니다.
- 업무일지 CSV는 현재 조건의 전체 업무를 내보내지만 물건은 업무당 대표 1건입니다. 관계를 복원하는 전체 백업을 대신하지 않습니다.
- ID 커서 수집은 여러 요청에 걸친 동일 시점의 DB 스냅샷이 아닙니다. 수집 중 이미 지난 커서 앞에 새로 생긴 고객은 다음 명부 갱신에서 보입니다. 기존 고객이 최근 업무·이름 정렬 변경 때문에 누락되는 문제를 해결한 것입니다.
- 업무의 동시 수정은 충돌을 차단하지만 자동 병합하지는 않습니다. 고객 수정도 충돌을 차단하며, 나머지 기록은 나중 저장이 앞선 변경을 덮을 수 있습니다.
- 작성 중 내용은 화면·이력 이동과 저장 실패에서 보호하지만, 브라우저 새로고침 뒤 자동 복구하는 초안 보관 기능은 없습니다. 새로고침·종료 전에 저장해야 합니다.

이번 점검으로 확인한 문제는 재현 조건과 회귀 검사에 연결했습니다. 이후 불편을 점검할 때도 출발 화면·입력 조건·선택 대상·저장 결과·복귀 위치를 함께 확인해야 하며, 기능 추가보다 이 사용 흐름의 안정성을 우선합니다.
