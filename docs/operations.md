# 집장부 운영 확인

이 문서는 소스 검증 이후 운영 환경에서 확인할 절차입니다. GitHub 푸시만으로 운영 배포·예약 실행·실제 DB 복원이 완료되지는 않습니다. 현재 배포 식별자와 확인 일시를 함께 기록하세요.

## 변경 반영 확인

1. `npm ci`, `npm run lint`, `npm test` 결과와 반영할 commit을 확인합니다. Node.js 24를 기준으로 검사합니다.
2. 신규 `0007`은 원문 보관 테이블과 고객 이력 source 식 인덱스를 추가합니다. runtime bootstrap 4도 같은 정의와 기존 원문 이행을 포함합니다. 운영에 반영할 때는 변경 전 백업이 있는지 확인합니다.
3. `0008`은 원본 도면 파일 정보를 추가합니다. runtime bootstrap은 5이며, 새 테이블은 기존 도면과 업무 자료를 변경하지 않습니다. PDF worker는 `predev`·`prebuild`에서 고정 의존성으로 생성됩니다.
4. 별도 가상 자료로 로그인, 고객·업무·할 일 수정, 삭제·복구, 목록·CSV를 확인합니다. 실 고객 기록을 테스트로 바꾸지 않습니다.
5. 오래 열어 둔 탭은 작성 내용을 보관한 뒤 새로고침해 새 클라이언트 계약을 읽습니다. 할 일 PATCH는 조회 시 받은 revision이 필요합니다.

## 예약 백업 확인

- 설정은 UTC `0 15 * * *`, 한국 시각 자정입니다. 소스·빌드 설정과 별도로 실제 배포 환경의 트리거 등록과 실행을 확인합니다.
- 하루 뒤 백업 목록에서 **접속일 자동 백업**의 날짜, 파일 크기와 다운로드 가능 여부를 확인합니다. 같은 날 사이트 방문으로 생성될 수도 있으므로 목록의 존재만으로 예약 성공이라고 단정하지 않습니다.
- 예약 실행 로그에서 성공과 실패를 확인하고, 정한 기간 동안 성공이 없거나 파일 크기가 크게 달라지면 원인을 확인합니다. 현재 앱이 별도 장애 알림을 자동 전송하지는 않습니다.
- 변경 전 백업 실패는 저장을 차단합니다. 변경 후 백업 실패는 로그에 남으므로 저장 성공과 백업 성공을 구분해 확인합니다.

## 격리 복구 훈련

설정에서 내려받은 JSON 또는 별도로 보관한 암호화 파일을 안전한 로컬 경로에 둡니다. 실제 고객 정보가 있으므로 저장소·이슈·검사 로그에 첨부하지 않습니다.

```bash
node scripts/check-backup.mjs /secure/path/jipjangbu-backup.json
```

암호화 파일은 해당 파일을 만든 `BACKUP_ENCRYPTION_KEY`를 보안 설정을 통해 환경에 제공해야 합니다. 키를 명령 인자나 저장소 파일에 적지 않습니다. 도구는 메모리의 별도 SQLite DB로 복원하고 건수·외래키·무결성·원문 연결 형식을 검사하며, 운영 DB를 변경하지 않습니다.

도면 파일이 있는 백업은 설정의 **백업 내려받기**로 원본 바이트까지 포함한 JSON을 받아 검사합니다. R2의 내부 암호화 스냅샷은 불변 도면 객체 참조를 보관하므로, 스냅샷 파일만 별도로 가져오면 원본 도면이 빠질 수 있습니다. 검사 도구는 원본 누락·크기·SHA-256 불일치를 거절합니다. `structure-files/` 원본은 90일 백업 정리 대상에서 제외하며 현재 자동 삭제하지 않습니다. 별도 장치에 보관할 때는 파일 포함 다운로드를 사용하세요.

현재 v1 백업에는 `listing_source_notes`도 포함합니다. 이전 v1 백업에서 해당 테이블이 없으면 기존 매물 원문과 이벤트를 바탕으로 초기 보관 자료를 재구성합니다. 형식·건수·관계가 깨진 자료는 성공으로 처리하지 않습니다.

실제 운영 복구 훈련은 별도 임시 DB에 복원한 뒤 고객, 업무와 모든 물건, 현재 매물·원문, 할 일, 휴지통, 도면 연결을 확인하는 단계까지 필요합니다. 마지막 복구 가능 시점과 소요 시간을 기록하고, 운영 전환 절차와 복귀 경로를 준비합니다. 메모리 검사 통과만으로 운영 DB 복구 성공을 보고하지 않습니다.

## 암호화 키 보관과 교체

- 과거 암호화 백업에는 그 파일을 만든 키가 필요합니다. 키와 백업의 보관 기간을 맞추고 안전한 별도 보관 위치에 기록합니다.
- 현재 앱 다운로드는 현재 `BACKUP_ENCRYPTION_KEY`를 사용합니다. 키를 바꾸기 전에 과거 파일의 복호화·별도 보관·필요 시 재암호화 계획을 마련합니다.
- 새 키로 만든 시험 백업의 격리 복구를 확인하고, 보관 중인 과거 백업도 이전 키로 검사할 수 있는지 확인합니다. 이전 키를 즉시 폐기하지 않습니다.
- 운영 계정·키·평문 백업을 CI나 공개 보고서에 넣지 않습니다. 검사 도구의 결과는 테이블별 건수만 공유합니다.
