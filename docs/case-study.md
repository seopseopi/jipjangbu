# 집장부 기술 사례: 엑셀의 업무 맥락을 웹으로 옮기기

집장부는 부동산 업무용 엑셀을 고객·업무·매물·일정이 연결된 웹 도구로 옮긴 프로젝트입니다.
핵심 과제는 표를 화면으로 바꾸는 것보다, **사용자가 찾고 읽고 고친 기록이 다른 화면에서도 같은 의미로 보이게 하는 것**이었습니다.

이 문서는 실제 피드백을 재현 조건, 설계 판단, 구현 근거와 검증 범위로 연결합니다.
주소 예시는 합성 표기이며, 실제 고객 정보·연락처·운영 인증정보는 포함하지 않습니다.

[서비스 소개](../README.md) · [엑셀 분석](excel-analysis.md) · [문서 모음](README.md)

## 출발점: 화면보다 먼저 정리한 데이터 관계

개발용 통합문서를 기준으로 불필요한 시트를 제외하고, 원본의 달력 VBA와 업무 연결 규칙을 대조했습니다.
업무 하나에 여러 물건이 연결되고, 매물 관련 업무가 현재 매물 상태와 가격을 바꾸는 구조를 유지했습니다.

| 기록 | 역할 | 설계상 구분 |
| --- | --- | --- |
| 고객·업무·물건 상세 | 누구와 언제 어떤 물건에 관해 일했는가 | 업무 본문과 물건별 속성을 분리하고 입력 순서 보존 |
| 매물 이벤트 | 매물에 영향을 주는 업무의 내용·날짜·상태 | 과거 정정과 새 변경 업무를 구별 |
| 현재 매물 | 이력으로부터 계산한 현재 조회용 상태 | 업무 저장·삭제·복구와 같은 원자적 작업에서 재계산 |
| 휴지통·백업 | 실수와 장애에 대비한 복구 자료 | 화면 단건 복구와 전체 데이터 백업은 별도 보호 수단 |

현재 매물만 직접 덮어쓰면 “가격은 바뀌었는데 이력이 없다”는 문제가 생깁니다.
따라서 업무·물건·매물 이벤트·현재 매물 갱신을 하나의 D1 batch로 묶었습니다.
이벤트는 수정될 수 있으므로 모든 변경 버전을 보관하는 완전한 이벤트 소싱이나 감사 로그라고 부르지는 않습니다.

근거: [데이터 스키마](../db/schema.ts), [업무 저장](../app/api/work-logs/data.ts), [매물 재계산](../db/listing-sync.ts), [정합성 검사](../tests/listing-history-consistency.test.mjs).

## 사례 1. 화면에 보이는 주소로 검색했는데 결과가 없었다

### 문제와 판단

화면은 `예시마을 106동 1503호`처럼 주소를 합쳐 보여주지만, 기존 검색은 건물명·동·호수를 따로 비교했습니다.
여러 물건이 연결된 업무에서는 두 번째 물건이 일치해도 첫 번째 물건을 대표로 보여주어 결과를 믿기 어려웠습니다.

검색의 기준을 저장 필드가 아니라 **사용자가 읽은 주소 표현**에 맞췄습니다.
단순히 공백을 지우고 문자열을 합치면 `1106동`을 `106동`으로 찾거나, 다른 두 물건의 동·호수를 섞을 수 있어 주소 조건을 구조적으로 분리했습니다.

### 구현

- `106동 1503호`, `106동1503호`, `106 1503`, `106-1503`를 주소 조건으로 해석합니다.
- 명시한 동·호는 전체 값을 비교하고, 한 물건 행에서 두 조건이 함께 맞아야 합니다.
- 업무일지·통합검색·매물 관리·불러오기 등에 같은 검색 함수를 적용합니다.
- 검색에 일치한 물건을 대표로 표시하되, 원래 물건 순서와 전체 목록은 보존합니다.
- 검색 중·통신 실패·정상 0건을 구분하고, 이전 결과를 새 조건의 결과처럼 표시하지 않습니다.

근거: [공통 주소 검색](../app/api/_search.js), [업무 목록 API](../app/api/work-logs/route.ts), [대표 물건 조회](../app/api/_queries.ts).

### 검증과 트레이드오프

실제 API 처리기를 합성 SQLite에 연결해 검색 결과·건수·페이지·일치 물건을 함께 검사했습니다.
비슷한 번호, 서로 다른 물건의 동·호 조합, 전화번호, `%`·`_` 문자도 부정 사례로 확인했습니다.
브라우저에서는 검색한 물건의 이력을 열고 돌아와 검색 조건이 유지되는 흐름을 확인했습니다.

주소 아닌 상담 내용 검색도 유지하므로, 본문에 주소가 적힌 업무가 함께 나올 수 있습니다.
자연어 검색이나 오타 교정은 아니며, 주소 접미사가 없는 숫자 일부는 부분 검색으로 남겨 두었습니다.

검증: [주소 검색 회귀 검사](../tests/property-search.test.mjs), [검색 화면 상태 검사](../tests/journal-search-state.test.mjs), [검색 점검 보고서](search-review.md).

## 사례 2. 내용을 보려고 눌렀는데 수정창부터 열렸다

### 문제와 판단

업무를 누르면 입력 폼이 열려 읽기와 수정이 섞였고, 여러 매물이 `외 N건`으로 숨겨져 업무 전체를 파악하기 어려웠습니다.
모든 매물을 펼친 뒤에는 반복되는 단지명과 좁은 카드가 또 다른 가독성 문제가 되었습니다.

**읽기는 기본 동작, 수정은 의도적으로 시작하는 동작**으로 분리했습니다.
정보를 숨기기보다 반복 표현을 줄이되, 현장 방문처럼 의미가 있을 수 있는 입력 순서는 바꾸지 않았습니다.

### 구현

- 업무일지·달력·검색·이력에서 내용을 먼저 읽고, 명시적인 수정 버튼으로 편집에 들어갑니다.
- 최대 10개 물건의 주소·가격·물건지·업소를 읽기 화면에서 펼쳐 보여줍니다.
- 연속된 같은 단지는 이름을 한 번 표시합니다. 뒤에 다시 나오는 단지를 앞쪽에 합치지는 않습니다.
- 업무 본문과 물건 목록을 분리하고, 실행 버튼이 긴 메모의 가로 폭을 차지하지 않게 합니다.
- 취소·저장 후 읽던 화면으로 돌아가며, 검색 조건·목록 범위·작성 중 초안을 보호합니다.

달력도 모든 업무를 같은 형식으로 줄이지 않았습니다.
엑셀 기준에 따라 매물 관련 업무는 주소, 계약 관련 업무는 주소와 물건지·업소, 일반 상담은 고객을 먼저 표시합니다.

근거: [업무 읽기 화면](../app/work-detail-view.tsx), [주소 그룹화](../app/property-display.ts), [공통 물건 표시](../app/work-summary-properties.tsx), [달력 표시](../app/calendar-subjects.tsx).

### 검증과 트레이드오프

열 물건의 전체 주소·원순서·각 이력 연결을 검사하고, PC와 390px 휴대폰·큰 글씨 모드에서 읽기와 수정 복귀를 확인했습니다.
모든 정보를 목록에 늘어놓지는 않습니다. 본문은 미리보기로, 전체 내용은 읽기 화면으로 단계화했습니다.
이는 저장된 원문을 줄이는 변경이 아니라 정보의 표시 밀도를 조정하는 변경입니다.

검증: [읽기 화면 검사](../tests/work-detail-read.test.mjs), [이동·복귀 검사](../tests/work-reader-navigation.test.mjs), [물건 표시 검사](../tests/work-summary-properties.test.mjs), [가독성 보고서](readability-review.md), [엑셀 표시 기준](excel-analysis.md).

## 사례 3. 저장은 됐는데 이력에서 수정 내용이 보이지 않았다

### 문제와 판단

과거 업무를 정정해도 상단의 엑셀 원본 메모와 업무일은 그대로여서 저장 실패처럼 보였습니다.
처음에는 최근 저장한 한 건을 상단에 보여줬지만, 사용자가 원한 것은 “마지막 한 건”이 아니라 엑셀처럼 이어 읽는 전체 이력이었습니다.

여기서 **업무가 발생한 날짜, 시스템에 저장한 시각, 현재 매물 상태**를 서로 다른 개념으로 정리했습니다.
최근에 저장했다는 이유로 과거 업무가 최신 매물 가격을 덮도록 바꾸지는 않았습니다.

### 구현

- 매물의 모든 업무 내용을 업무일 최신순으로 이어 읽는 누적 메모를 기본으로 표시합니다.
- 개별 업무 목록은 접기 영역으로 옮겨 같은 내용을 두 번 펼쳐놓지 않습니다.
- 개별 기록에서 업무일과 최근 저장 시각을 구분하고, 저장 시각이 없는 원자료는 추측하지 않습니다.
- 같은 날짜·업무구분의 구조화된 기록에 포함된 원본 메모만 중복 표시에서 제외합니다.
- 원본에만 남은 부분이나 해석할 수 없는 형식은 보관 메모로 유지하며 원본 저장값을 바꾸지 않습니다.
- 새 매물 변경은 새 업무로 추가하고, 과거 정정은 기존 업무를 수정하는 흐름을 구별합니다.

근거: [누적 이력 표시](../app/listing-history-summary.tsx), [저장 시각 해석](../app/history-timestamps.ts), [현재 상태 선정](../db/listing-sync.ts).

### 검증과 트레이드오프

과거 정정·미래 업무일·날짜 경계·원본만 있는 매물·일부만 중복된 메모를 합성 자료로 검사했습니다.
날짜와 업무구분만 같다는 이유로 서로 다른 메모를 없애지 않는 것이 보존 기준입니다.

현재 누적 이력은 업무 기록의 연속이지, 각 업무를 수정하기 전후의 모든 버전은 아닙니다.
수정 이전 문장까지 되돌리는 버전 복원은 별도의 감사 이력 설계가 필요합니다.

검증: [누적 메모 검사](../tests/listing-history-summary.test.mjs), [원본 중복 검사](../tests/listing-source-deduplication.test.mjs), [시각 검사](../tests/history-timestamps.test.mjs), [이력 표시 개선 기록](readability-review.md).

## 사례 4. 느린 로딩과 “창이 안 뜬다”를 함께 다뤘다

### 문제와 판단

운영 로그에서 일부 조회가 CPU 시간 1~4ms에 비해 약 4.5~18초 대기하다 취소되었고, 정상 완료한 요청도 있었습니다.
로그만으로 단일 원인을 확정하지 않고, 데이터 준비·창 복귀·요청 취소가 맞물리는 경로를 확인했습니다.
수정창은 고객명부와 업무 상세가 모두 도착한 뒤에야 나타나 클릭이 무시된 것처럼 보일 수 있었습니다.

### 구현

- 홈은 홈 데이터와 분류부터 읽고, 전체 고객명부는 업무 입력창이 처음 필요할 때 읽습니다.
- 입력 폼이 준비되지 않았어도 취소 가능한 준비창은 즉시 표시하고, 실패 시 같은 위치에서 재시도합니다.
- 창 복귀에는 완료 캐시만 비워 진행 중 요청의 취소·재시작 반복을 줄입니다.
- 이미 진행 중인 요청을 공유했다면 완료 후 다시 조회해 다른 기기의 변경을 놓치지 않게 합니다.
- 저장·로그아웃·인증 만료에는 읽기를 폐기하고, 수정 전의 늦은 응답이 새 상태를 덮지 못하게 합니다.
- 서버 DB 준비는 진행 중 Promise가 아니라 완료 여부만 캐시하여 요청 간 D1 I/O 공유를 없앱니다.

근거: [브라우저 읽기 캐시](../app/client-api.ts), [업무창·창 복귀 처리](../app/work-manager.tsx), [DB 초기화](../db/bootstrap.ts), [요청 생명주기 설명](performance.md).

### 검증과 수치 해석

합성 자료를 둔 로컬 Worker·D1·R2와 실제 Chromium에서 명부 응답을 보류하고 취소·재시도·늦은 응답을 재현했습니다.
응답 대기 중 focus 이벤트 6회는 기존 조회 1회와 완료 후 최신 조회 1회로 합쳐졌고, 취소한 수정창은 다시 열리지 않았습니다.

| 측정 대상 | 확인한 변화 | 해석 범위 |
| --- | --- | --- |
| 홈 첫 기본 조회 | 3개 → 2개 | 별도의 홈 할 일 조회를 포함하면 4개 → 3개 |
| 분류 / 통합검색 DB 호출 | 각각 2회 / 3회 → batch 1회 | HTTP 요청 수가 아니라 서버 내부 DB 왕복 |
| 합성 고객 4,000명·업무 160,000건 명부 SQL | 중앙값 28.91 → 3.80ms | 로컬 SQLite; 네트워크·서버 기동·렌더링 제외 |

명부 조회는 페이지 고객만 집계하도록 바꾸고, 결과 일치와 실행 계획을 함께 검사했습니다.
초기 정적 의존성 gzip 합계는 준비창·오류 처리 추가로 172,087 → 172,441B로 소폭 증가했습니다.
이번 결과를 번들 축소나 전체 사이트의 특정 배수 가속으로 설명하지 않습니다.
동일 네트워크 조건의 운영 전체 로딩 시간 전후 비교는 수행하지 않았습니다.

검증: [클라이언트 경합 검사](../tests/client-performance.test.mjs), [느린 창 열기 검사](../tests/frontend-loading.test.mjs), [초기화 검사](../tests/runtime-performance.test.mjs), [SQL 성능 검사](../tests/query-performance.test.mjs), [브라우저 검증 보고서](loading-e2e-review.md).

## 사례 5. 삭제 버튼보다 복구할 수 있는 삭제가 필요했다

### 문제와 판단

기존 삭제는 수정창 하단에 있어 찾기 어려웠고, 사용자가 직접 되돌릴 휴지통이 없었습니다.
한 업무가 여러 매물 상태에 영향을 주기 때문에 행 하나를 지우는 것만으로는 안전한 삭제가 되지 않았습니다.
먼저 PRD로 대상·영향·복구·제외 범위를 정하고, 단건 삭제를 휴지통 이동으로 통일했습니다.

### 구현

- 읽기 화면에서 삭제를 시작하되, 저장된 내용과 연결 매물·영향을 먼저 확인합니다.
- 업무·물건·이벤트·필요한 원본 메모를 스냅샷으로 보관하고 삭제·매물 재계산을 원자적으로 처리합니다.
- 확인한 내용의 SHA-256 값과 트랜잭션 시점 SQL 재검증으로 확인 이후의 변경을 감지합니다.
- 복구는 원래 관계를 되살리고 현재 매물을 다시 계산하며, 현존하는 같은 ID의 자료를 덮어쓰지 않습니다.
- 활성 업무뿐 아니라 휴지통의 복구 대기 기록이 참조하는 고객도 삭제하지 못하게 합니다.
- 영구삭제·자동 비우기·일괄삭제는 제공하지 않고, 처리 중 중복 클릭과 창 닫기를 막습니다.

근거: [삭제 PRD](deletion-prd.md), [스냅샷·원자적 삭제/복구](../db/deletion-store.ts), [확인창](../app/deletion-dialog.tsx), [휴지통](../app/trash-view.tsx).

### 검증과 트레이드오프

격리된 실제 Worker·D1·R2에서 두 매물의 업무를 삭제해 이전 가격으로 돌아가는지, 복구 후 날짜·관계·가격이 돌아오는지 확인했습니다.
확인 후 동시 수정은 409로 차단하고, 강제 SQL 실패의 전체 롤백·백업 실패 시 쓰기 차단도 검사했습니다.
브라우저 E2E에서는 Esc가 뒤의 읽기창까지 닫히는 문제와 마지막 매물 삭제 후 잘못된 주소 오류를 찾아 수정했습니다.

휴지통은 삭제 복구 기능이지, 동시 편집의 모든 충돌을 해결하는 기능은 아닙니다.
변경 전 백업 실패 시 쓰기를 중단하므로 가용성보다 자료 보존을 우선하며, 저장 지연이 생길 수 있습니다.

검증: [삭제 안전성 검사](../tests/deletion-safety.test.mjs), [삭제 UI 검사](../tests/deletion-ui.test.mjs), [백업 보호](../worker/security.ts), [삭제·복구 E2E 보고서](deletion-e2e-review.md).

## 2026-10-31 화면 리뉴얼

이후 화면 검토에서 아이보리 배경과 흰 섹션, 큰 기본 글씨, 둥근 모서리로 화면 규칙을 통일했습니다. 집·장부 단색 심볼과 사무소명을 사용하고 검색과 새 업무 등록을 나란히 배치했습니다. 기존 고객·업무·매물·세대 연결과 저장 검증은 유지했습니다.

업무일지의 기간 선택과 목록 CSV 내보내기는 제거하고, 업무일지 5건·매물 10건씩 페이지를 넘기도록 바꿨습니다. 서버의 100건 단위 증분 조회와 고객 목록의 더보기는 유지했습니다. 달력은 하루 4건 제한을 없애 모든 업무를 직접 표시하며 업무구분 색상과 오늘 날짜 숫자 표시를 구분했습니다. 홈 할 일도 5건 제한을 없애고 새 할 일 추가 버튼과 필수 예정일·선택 메모를 적용했습니다.

이 절은 현재 화면 변경을 기록하며, 앞 절의 과거 측정치와 검증 범위를 새 디자인의 측정 결과로 바꾸지는 않습니다.

## 검증을 읽는 기준과 남은 과제

기준 커밋 `907d299`의 전체 자동 검사는 **416개 통과** 기록을 기준으로 합니다. 이 문서 작성 과정에서 재실행한 수치는 아닙니다.
자동 검사 수를 모든 사용 흐름의 무결성이나 코드 커버리지로 해석하지 않습니다.
실제 API/SQL 검사, 제어된 비동기 UI 검사, 합성 자료의 실제 브라우저 검증은 서로 다른 범위를 확인합니다.

재현 진입점: [검사 스크립트](../package.json), [CI](../.github/workflows/ci.yml), [전체 흐름 점검](workflow-review.md).

- 업무·고객·할 일 수정은 충돌을 감지해 저장을 막습니다. 자동 병합과 수정 전 버전 복원은 남은 데이터 보호 과제입니다.
- 백업은 이용 시 일일 실행과 변경 전후 실행이며 예약 트리거 설정이 포함됩니다. 운영 환경에서 예약 실행을 별도로 확인해야 합니다.
- 원문 보관과 구조 도면을 포함한 18개 테이블의 암호화 백업과 단건 휴지통 복구를 검사했지만, 운영 환경 전체 DB 복원·재해 복구 E2E는 수행하지 않았습니다.
- 브라우저 새로고침 후 자동 복구하는 초안 저장은 없으며, 모든 기기·브라우저와 장기간 대량 사용을 검증한 것은 아닙니다.

이 프로젝트에서 중요한 결과는 기능 개수보다 **사용자 불편을 재현 가능한 조건으로 바꾸고, 표시·저장·복구·복귀 흐름을 함께 고친 과정**입니다.
남은 과제도 같은 기준으로, 데이터 보존과 사용자가 확인할 수 있는 상태를 우선해 다룹니다.
