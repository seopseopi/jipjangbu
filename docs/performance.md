# 집장부 성능 개선

## 개선한 경로

| 항목 | 이전 | 변경 후 |
|---|---|---|
| 화면 전환·정렬·필터 | 조회 시작 전 300ms 대기 | 즉시 조회, 검색 입력만 250ms 지연 |
| 같은 조회의 동시 요청 | 각각 서버 요청 | 하나의 요청 공유 |
| 반복 화면 이동 | 같은 자료 재전송 | 페이지 메모리에서 최대 15초 재사용 |
| 홈 표시 | 고객명부·분류까지 모두 기다림 | 홈 데이터가 도착하면 먼저 표시 |
| 업무 요약의 상관 하위 조회 | 첫 물건 속성 8개 + 건수 | 대표 물건·건수·전체 물건 JSON, 총 3개 |
| 업무 목록과 전체 건수 | 순차 DB 왕복 2회 | 일관된 snapshot으로 batch 1회 |
| 홈 데이터 | 개별 DB 왕복 5회 | batch 1회 |
| 준비된 DB의 새 서버 시작 | SQL 136문장·왕복 4회 | 확인 SELECT 1회, 쓰기 없음 |
| 변경 전후 전체 백업 | 테이블별 순차 조회 | 원문 보관·도면·휴지통을 포함한 테이블 19개를 batch 1회로 읽기 |
| 고객 선택 검색 | 입력·정렬 비교마다 문자열 가공 | 명부 변경 때만 전처리, 순위별 선형 검색 |
| 통합검색·현황 화면 코드 | 홈에 함께 로드 | 처음 필요할 때 로드 |

## 2026-09-14: 느린 초기 조회와 업무 창 열기 개선

운영 로그에서 일부 조회는 서버 CPU 시간이 1~4ms인데도 약 4.5~18초 대기 후 취소되었고, 같은 경로가 정상 완료된 경우도 확인했습니다. 무거운 화면 코드만의 문제로 단정하지 않고 요청 대기·취소 경로를 함께 수정했습니다. 취소 로그만으로 서버 장애나 단일 원인을 확정할 수는 없습니다.

| 경로 | 변경 내용 |
|---|---|
| 처음 홈 열기 | 홈·분류 조회만 먼저 수행. 전체 고객명부는 업무 입력창을 처음 사용할 때 조회하며, 사용한 뒤 저장·창 복귀 갱신은 유지 |
| 업무 등록·수정 열기 | 데이터가 준비되기 전에도 취소 가능한 준비창을 즉시 표시. 실패 시 같은 창에서 재시도하고, 취소한 창은 늦은 응답으로 다시 열리지 않음 |
| 창 복귀 | 완료된 읽기 캐시만 비워 진행 중 조회의 취소·재시작 반복을 방지. 기존 요청을 공유했다면 완료 후 추가 조회로 최신성 확보 |
| 서버 DB 준비 | 성공 여부만 캐시. 다른 요청의 진행 중 D1 Promise를 기다리지 않아 첫 요청 중단이 후속 요청의 준비를 막지 않음 |
| 고객명부 | 전체 고객의 업무를 집계하는 대신 해당 페이지 고객만 기존 인덱스로 집계 |
| 매물 종류 필터 | 선택한 종류가 있을 때만 동등 조건을 넣어 기존 인덱스 활용 |
| 분류·통합검색 | D1 호출 각각 2회·3회를 batch 1회로 통합. 검색 범위·주소 표기·정렬·반환 필드는 유지 |

서버 초기화 변경은 Cloudflare의 [요청 간 I/O 공유 제한](https://developers.cloudflare.com/workers/observability/errors/)에 맞춰 진행 중 I/O 대신 완료 상태만 보관합니다. 준비된 서버에서는 추가 DB 확인이 없고, 준비 여부를 처음 확인하는 동시 요청은 각자 확인 SELECT를 할 수 있습니다.

전체 고객명부를 없애거나 일부 고객만 선택하게 만든 변경은 아닙니다. 기존 ID 커서 페이지 조회로 전체 명부를 읽으며, 폼 준비와 창 복귀 조회가 겹치는 경우도 회귀 검사합니다. 변경 요청·로그아웃·인증 만료에서는 기존처럼 진행 중 읽기를 폐기하여 수정 전 자료가 다시 나타나지 않게 합니다.

`tests/query-performance.test.mjs`에는 합성 고객 4,000명·업무 160,000건의 명부 쿼리 비교와 매물 필터의 실행 계획 검사가 추가되어 있습니다. 이 SQL 측정은 로컬 SQLite만의 수치이며 운영 화면 전체가 같은 배수로 빨라진다는 의미는 아닙니다.

업무일·고객·업무구분 인덱스 3개는 같은 앞부분에 정렬 열을 포함한 복합 인덱스로 교체했습니다. 월별 조회는 날짜를 `substr`로 계산하지 않고 날짜 범위로 검색합니다. 기존 정렬·검색·전체 건수·CSV 데이터 계약은 유지합니다.

## 데이터와 보안 원칙

- 캐시는 서버 DB를 대체하지 않습니다. 브라우저 페이지 메모리에만 보관하고 15초·32개·약 2MB로 제한합니다. 저장소 파일이나 localStorage에 업무 데이터를 남기지 않습니다.
- 변경 요청 전후, 인증 만료, 로그아웃, 다른 창에서 복귀할 때 읽기 캐시를 비웁니다. 변경 이전에 시작한 늦은 응답이 새 결과를 덮지 못하게 합니다.
- 인증·백업·외부 URL·사용자 지정 요청 옵션은 읽기 캐시를 공유하지 않습니다. 서버 실행에서는 이 브라우저 캐시를 사용하지 않습니다.
- 변경 전 안전 백업에 실패하면 기존처럼 변경을 중단합니다. 변경 후 백업, AES-GCM 암호화, 90일 자동 보관은 유지합니다.
- 초기화 완료 표식은 업무 자료가 아닌 내부 메타데이터입니다. 백업에는 넣지 않으며, 복원 후 필요한 표·인덱스가 없으면 다시 준비합니다. 기존 DB가 비었다고 예시 고객·업무를 재주입하지 않습니다.
- 향후 기본 분류나 bootstrap 스키마를 바꿀 때는 `db/bootstrap.ts`의 `BOOTSTRAP_VERSION`도 올려야 합니다. 스키마와 생성 마이그레이션, runtime 초기화 정의를 함께 유지합니다.

## 재현 가능한 검증

`npm test`는 타입 검사·배포 빌드·회귀 테스트를 실행합니다. `npm run lint`는 별도 코드 검사를 수행합니다.

`tests/query-performance.test.mjs`는 실제 SQLite에서 이전/새 쿼리의 공통 값이 같은지 비교하고, `EXPLAIN QUERY PLAN`으로 복합 인덱스 사용·반복 조회 감소·불필요한 정렬 제거를 검사합니다. 업무 12,000건·물건 상세 24,000건 중 최근 1,000건 조회를 측정합니다. 전체 물건 JSON을 추가한 2026-09-13 실행 예는 기존 약 4.0ms, 새 쿼리 약 4.5ms였습니다. 더 많은 물건 정보를 한 응답으로 제공하는 변경이며, 더 빠르다는 보장값이 아닙니다. 이는 DB 쿼리만의 로컬 측정값으로 실행 환경마다 달라집니다.

`tests/client-performance.test.mjs`는 중복 요청·만료·취소·저장 경합·인증 만료·캐시 크기를 실제 fetch 동작으로 검사합니다. `tests/runtime-performance.test.mjs`는 초기화 재시도·복원·백업 내용과 실패 시 변경 차단을 검사합니다.

필터를 바꾸는 중의 더보기는 조회 조건과 첫 페이지 완료 여부로 차단하며 `tests/client-paging.test.mjs`로 검증합니다. 저장 때문에 진행 중인 통합검색이 취소되면 자동 재시도하고, 할 일·분류 저장 후에도 검색을 새로 갱신합니다.

업무 저장과 창 복귀 시에는 이미 펼친 목록 범위만 다시 읽습니다. 1,000건을 넘으면 API 한도에 맞춰 나눠 읽고, 중간 실패 시 부분 결과로 기존 목록을 덮지 않습니다(`tests/work-window.test.mjs`). 새 고객·매물 이력 패널은 열 때만 코드를 불러오고 고객 이력은 10건씩 조회합니다. 닫힌 패널의 늦은 응답, 중복 요청, 조회 중 저장에 따른 취소·재시도를 검사합니다(`tests/related-history.test.mjs`).

`tests/history-navigation.test.mjs`는 실제 화면의 비동기 열기 함수를 추출해 A→B 연속 클릭의 역순 응답, 창을 닫은 뒤 늦은 응답, 저장 후 이력 유지, 마지막 매물 이력 삭제를 검증합니다. `tests/customer-draft.test.mjs`는 고객 작성 내용의 변경 감지와 닫기 보호를 검사합니다. 이 검사는 브라우저에서의 시각적 QA를 대체하지 않습니다.

`node scripts/measure-client.mjs`는 빌드 결과에서 초기 정적 의존성과 압축 크기를 계산합니다. 지연 로딩 파일은 초기 크기에 넣지 않습니다. HTML·이미지·별도 전역 CSS·폰트까지 포함한 브라우저 전체 다운로드 측정은 아니므로 사이트 총 전송량으로 해석하지 않습니다.

## 2026-10-29: 실제 고객 이력과 관리 목록

고객 이력의 직접 연결과 물건지 연결을 후보 업무 ID의 UNION으로 먼저 구합니다. `trim(source), work_log_id` 식 인덱스로 전체 업무의 상관 EXISTS 스캔을 피하며 기존 중복 제거·공백·검색·필터·정렬 결과를 비교합니다.

고객·매물 API는 limit/total/hasMore를 반환하며 관리 화면은 첫 100건만 표시합니다. 더보기와 이미 펼친 범위의 갱신은 현재 조건만 사용합니다. CSV는 별도 1,000건 단위 전건 수집을 유지하고 중간 실패·반복 페이지는 다운로드를 중단합니다. 업무 폼의 고객 ID 커서 명부는 이 화면 페이징과 별개입니다.

`tests/query-performance.test.mjs`는 실제 실행 계획과 결과를, `tests/managed-navigation-improvements.test.mjs`는 첫 표시·더보기 경합·1,201건 CSV·중간 실패를 검사합니다. 합성 SQL 측정은 운영 D1 지연시간의 보장값이 아닙니다.
